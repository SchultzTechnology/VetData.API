Standard Data API

Read Covetrus Connect Marketplace data through a RESTful OData v3 API. Authenticate with a CIAM OAuth 2.0 access token, identify the practice with an Installation request header, and query entity collections beneath https://api.vetdata.net/v2.

OData v3 Bearer token Practice-scoped reads JSON or ATOM
Scope: This page documents the Standard Data API, not the separate Data Delivery or Writeback services. It is a human-readable reference, not a machine-readable OpenAPI specification.

Quick start

  1. Obtain your CIAM username and password. These differ from Basic Auth credentials; contact techops@vetdata.com if needed.
  2. POST to the CIAM token endpoint. Save the response’s access_token and expires_in.
  3. Determine the practice’s installation ID using InstallationList and your integration’s practice-mapping process.
  4. Call an entity collection with Authorization: Bearer …, Installation: …, and the desired Accept header.
  5. Reuse the token until shortly before expiration. Page and filter entity requests as appropriate for your integration.

Authentication

OAuth 2.0 authentication is required for the Standard Data API. The documented CIAM flow exchanges a CIAM username and password for an access token.

Setting Value
Token URL https://auth.covetrus.com/oauth/token
Grant type http://auth0.com/oauth/grant-type/password-realm
Token request body application/x-www-form-urlencoded
API authorization Authorization: Bearer ACCESS_TOKEN
Expiration Use the response’s expires_in, in seconds. There is no documented refresh-token mechanism; request a new access token when needed.

The published client_id, audience, realm, grant_type, and covetrus_product_code values are not treated as secrets by Covetrus. Protect your CIAM username, password, and issued access token.

Request conventions

Header Value When used
Authorization Bearer ACCESS_TOKEN Authenticated API calls
Installation Practice installation GUID Data requests beneath /v2
Accept application/json JSON light
Accept application/json;odata=verbose JSON Standard / verbose
Accept application/atom+xml ATOM
Metadata exception: Do not send Accept: application/json when requesting /v2/$metadata. The source documentation does not specify a required alternative Accept value.

Entity names and their fields are defined by the separate Data Schema documentation and the API metadata. Query examples below illustrate OData v3 usage; confirm supported query behavior and response shapes for the entity you are integrating.

Endpoints

POST https://auth.covetrus.com/oauth/token Obtain a CIAM access token

Send form-encoded credentials. The response contains an access_token and expires_in, among other fields.

Required headers

Accept: application/json
Content-Type: application/x-www-form-urlencoded

Required form fields

Field Value
grant_type http://auth0.com/oauth/grant-type/password-realm
client_id p9vvyF08lLYNzAfcDiWuLJf4mWGdGm2M
audience https://vetdata.net
username Your CIAM username
password Your CIAM password
realm PartnersDB
covetrus_product_code Vetdata

cURL example

curl --request POST "https://auth.covetrus.com/oauth/token" \
  --header "Accept: application/json" \
  --header "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode \
    "grant_type=http://auth0.com/oauth/grant-type/password-realm" \
  --data-urlencode "client_id=p9vvyF08lLYNzAfcDiWuLJf4mWGdGm2M" \
  --data-urlencode "audience=https://vetdata.net" \
  --data-urlencode "username=${CIAM_USERNAME}" \
  --data-urlencode "password=${CIAM_PASSWORD}" \
  --data-urlencode "realm=PartnersDB" \
  --data-urlencode "covetrus_product_code=Vetdata"

Set CIAM_USERNAME and CIAM_PASSWORD in your shell before running. Avoid storing credentials in checked-in files or shell history.

GET https://api.vetdata.net/InstallationList List installations

Returns a list of installations. This endpoint is separate from the practice-scoped /v2 entity collections.

Example

curl "https://api.vetdata.net/InstallationList" \
  --header "Authorization: Bearer ${ACCESS_TOKEN}" \
  --header "Accept: application/json"
The supplied endpoint description does not spell out InstallationList-specific header requirements or its response schema. This example uses the documented bearer scheme for Standard Data API access; verify any additional requirements with Covetrus.
GET https://api.vetdata.net/v2/$metadata Retrieve API metadata and schema

Inspect entity types and schema information. Do not set Accept: application/json on this request.

Example

curl 'https://api.vetdata.net/v2/$metadata' \
  --header "Authorization: Bearer ${ACCESS_TOKEN}"

The supplied overview does not specify whether the metadata endpoint requires an Installation header. Add one if required in your environment; do not assume metadata uses the same response format as entity data.

GET https://api.vetdata.net/v2/{EntityName} Read practice-scoped entity data

Substitute a defined entity collection, such as Addresses, Phones, or ClientPatientRelationships. Supply the practice’s installation GUID in the Installation header.

Required request headers

Installation: YOUR_INSTALLATION_GUID
Accept: application/json
Authorization: Bearer YOUR_ACCESS_TOKEN

Example: first 100 addresses

curl 'https://api.vetdata.net/v2/Addresses?$top=100' \
  --header "Installation: ${INSTALLATION_ID}" \
  --header "Accept: application/json" \
  --header "Authorization: Bearer ${ACCESS_TOKEN}"

The Standard Data API supports filtering, entity expansion, pagination, and diffing using API metadata datetime fields. OData query options use names such as $top, $filter, and $expand; consult the API metadata and entity-specific documentation before relying on a particular query or navigation property.

Do not confuse API variants: Standard Data API results represent present-state data. The separate Data Delivery API focuses on bulk ETL and transaction-log IDs; its query and historical-data behavior does not apply here.

Incremental sync guidance

The Standard Data API documentation describes diffing with API metadata datetime fields and pagination. The example entities expose APICreateDate, APILastChangeDate, and APIRemovedDate.

  1. Perform an initial, paginated load for each needed entity.
  2. Track a successful sync checkpoint for each installation and entity.
  3. Query relevant API datetime fields for subsequent changes, using the supported OData filters for that entity.
  4. Account for nullable change and removal fields; avoid relying on APILastChangeDate alone to discover every new record.
  5. Confirm removal visibility, filter syntax, pagination behavior, and checkpoint boundaries before using the results for deletion or reconciliation.
The supplied pages do not provide a complete, guaranteed delta query or deletion contract. In particular, a field named APIRemovedDate does not by itself establish when removed rows remain queryable. Validate this behavior before implementing production sync.

Errors and operational notes

Situation Recommended response
Expired token; API returns 401 Obtain a new token and retry as appropriate. Refresh a few minutes before the documented expiry.
Token acquisition fails Check CIAM credentials and request fields; contact Vetdata support if authentication still fails.
Many calls in a short period Cache and reuse the access token. Do not request a new token for every API call.
Highly parallel requests Check outbound connection limits and queues. A request delayed before reaching the API may encounter token expiry.

The CIAM guidance notes Auth0 login throttling, including limits after repeated incorrect passwords or frequent login attempts. Avoid aggressive token-request retries.

A long-running API request can finish after token expiry if the service receives and processes its token before it expires. Refreshing shortly before expiry still reduces race conditions.
